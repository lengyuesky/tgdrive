# Bot 收件多目录与重命名设计

状态：完整方案已于 2026-11-10 确认，已实现并于 2026-11-11 完成隔离验证，见 [验收记录](bot-inbox-verification-20261111.md)。用户分别确认 Q1–Q4、Q5–Q12 和最后一轮 Q13–Q17，形成整体共同理解；下文记录本次实现与验收依据。

## 用户已提出的需求

- 同一收件类型可以配置多个收件目录。
- 用户向收件 Bot 发送文件后，Bot 通过消息让用户手动选择保存目录。
- 存储时提供重命名选项。

术语见 [领域术语](../GLOSSARY.md)。收件目录属于 TGDrive 网盘目录树；Telegram 存储频道是文件内容的存储位置，两者是不同概念。

## 改动前的事实

现有收件支持白名单用户私聊和当前存储频道直发。私聊按 Telegram 会话 ID 检查全局白名单，空名单不收件；群聊不是收件入口。频道入口有独立开关。见 [收件入口](../src/inbox.rs)、[配置](../src/extras.rs) 和 [部署说明](deployment.md)。

两种入口共用默认、视频、图片、书籍目录及自定义后缀规则。每个内置类型和每条自定义规则目前只配置一个目录。自定义类型名称忽略大小写唯一，同一后缀不能分配给多条规则，因此不能靠重复规则实现同类型多目录。目录按路径配置，保存时不要求已存在，收件时自动创建。见 [规则模型与校验](../src/extras.rs) 和 [收件设置页面](../frontend/src/views/admin/InboxSection.vue)。

分类依据文件名后缀，自定义规则优先，多段后缀以更具体的匹配为先，随后匹配视频、图片、书籍，最后使用默认目录。音频没有内置类型，可用自定义后缀规则分类。当前入库使用最终传入的文件名分类，因此新增重命名时需要明确是否沿用原文件类型。

私聊收到文件后，用 `file_id` 在 Telegram 内重发至存储频道，登记网盘后回复路径；频道直发登记已有消息。现有流程没有让用户在入库前选目录或改名的阶段，也没有按钮回调、文本回复解析或待操作会话。见 [收件处理和消息结构](../src/inbox.rs)。

相册和连发按消息逐文件处理，没有相册分组或连发聚合。同一条视频消息中的多个清晰度先按有效文件引用及像素面积择优，只处理选中的一个版本；这不是对多条视频消息进行去重或合并。

现有同名收件在创建上传占位时自动尝试 `(1)` 至 `(999)`。该预检查不构成最终提交时的不覆盖保证：收件未创建禁止覆盖的上传会话，普通提交在两阶段之间出现同名文件时仍可能替换该文件。新流程需要明确最终提交的冲突行为，不能仅在展示操作消息时查重。见 [收件选名与提交](../src/inbox.rs) 和 [上传提交](../src/db/upload.rs)。

收件游标及死信持久化，但私聊没有来源消息与完成文件的幂等映射，也没有等待、过期或取消状态。顺序更新处理不能等待用户回复而阻塞后续收件；现有上传占位在启动清理中可能被回收，不能直接视为长期待选择记录。这些是需要处理的实现影响，持久化期限和恢复体验尚待用户决定。

## 第一轮已确认的行为

| 编号 | 建议 |
| --- | --- |
| Q1 | Bot 私聊启用手动选择及重命名；频道直发继续自动归类 |
| Q2 | 默认、视频、图片、书籍和自定义类型均可配置多个目录；沿用现有分类优先级，展示匹配类型的目录；无法分类时展示默认类型的目录 |
| Q3 | 文件收到后展示操作消息，用户选择目录、按需修改网盘文件名，再点击“确认存储”；只有一个目录时也能重命名；提供取消操作 |
| Q4 | 相册及连续发送按文件分别展示操作消息，分别选择目录和重命名；同一视频消息继续择优，只展示一个文件的操作消息 |

## 第二轮已确认的行为

| 编号 | 建议 |
| --- | --- |
| Q5 | 用户回复文件主体名，保留原文件完整后缀，包括已识别的 `tar.gz`；分类继续使用原始文件名；每次输入通过对指定操作消息的回复关联到一份文件 |
| Q6 | 最终提交同名时自动编号，成功回执显示实际路径；提交全程禁止覆盖已有文件或目录，并在提交边界保证该约束 |
| Q7 | 从收到文件起等待 24 小时，待办及已选目录、名称持久保存，重启后在剩余期限内继续；取消或过期结束待办，不自动入库，保留用户原 Telegram 消息 |
| Q8 | 每种类型指定一个“自动收件目录”，频道直发使用它；旧单目录原样迁移为唯一候选及自动收件目录；私聊单目录预选，多目录必须用户点选 |
| Q9 | 按管理页配置顺序展示目录名，同名时附上级目录区分；操作消息展示已选完整路径；每种类型最多 20 个候选目录，每页 6 个，可翻页 |
| Q10 | 收件目录跟随文件夹的重命名和移动；已选路径变化时更新消息并重新确认；目录删除或从配置移除时重新选择；确认存储时按最新类型配置校验原始文件名对应的候选目录，不静默重建失效的旧路径 |
| Q11 | 失败保留已选目录和名称并提示原因，可安全重试时提供手动重试；系统设置可查看待确认或失败收件、取消待办、重发操作消息；上游结果不确定时不得盲目重复转存 |
| Q12 | 每个白名单用户最多 50 份未结束收件，实例合计最多 500 份；超限时 Bot 明确提示，本次不创建待办，保留原 Telegram 文件消息 |

## 第三轮已确认的行为

| 编号 | 建议 |
| --- | --- |
| Q13 | 开始 Telegram 转存前可以取消；开始后锁定操作，等待成功或明确失败。开始前检查 24 小时截止时间，已开始的工作不因等待期限届满而中断；工作使用开始时绑定的 Bot、端点及频道完成 |
| Q14 | 关闭私聊收件后暂停未开始转存的待办，24 小时期限继续计时，重新启用后可继续；白名单移除则结束该用户未开始转存的待办。更换成另一个 Bot 时结束旧 Bot 的未开始待办并提示重新发送；同一 Bot 更换端点或存储频道保留待办，在下一次工作开始前校验并使用最新配置 |
| Q15 | Telegram 请求可能已经产生副本、但返回结果丢失时，标为“待核实”，禁止对该请求再次转存。此状态保留到人工结束，可查看并结束；结束不承诺删除无法确认的 Telegram 副本，管理员依据频道实际结果决定是否重新发送文件 |
| Q16 | 成功、取消、过期等已结束收件记录保留 30 天，之后清理记录；已入库网盘文件不受记录清理影响。旧操作消息点击后显示已结束、已过期或结果路径，不重新触发存储 |
| Q17 | 正常重启继续恢复仍有效的待办；从数据库备份恢复时，恢复出的旧未完成待办统一结束并标记恢复后失效，不重放可能已经发生的转存操作。用户重新发送文件后形成新请求；沿用现有备份恢复安全模式 |

## 已确认行为导出的实现约束

- 待确认请求独立于网盘上传占位持久保存，用户确认前不生成存储频道副本，不把待办展示为网盘文件；依据 [ADR-0005](adr/0005-persistent-inbox-requests.md)。
- 收件目录以文件夹身份绑定并展示当前路径，目录删除后不静默重建旧目录；依据 [ADR-0006](adr/0006-inbox-directory-identity.md)。旧配置的未创建目录可在首次迁移绑定时创建；路径被文件占用时明确报错，不能因此丢弃其他有效规则。
- 类型至少保留一个候选目录及一个有效自动收件目录；同类型中重复的目录不形成重复按钮。规则名称、后缀唯一性及多段后缀优先级继续校验。
- 原始文件名用于按最新规则分类；改名输入只决定网盘文件名主体，不能把目录路径当作文件名。无效或空输入提示用户重新输入并保留已有选择。
- 确认存储时复查请求身份、当前白名单、当前候选目录与目标文件夹身份，并以原子提交保证同名编号及不覆盖；收到重复按钮回调不得再次发起相同请求的转存。
- 转存已明确成功、但网盘登记或回复失败时，恢复与重试复用已有副本或已完成结果；回执发送失败不能将已成功入库改为未存储。
- 处理待办与接收更新分离，接收完成并持久记录后即可推进该 Bot 的游标；更新游标与原消息身份按 Bot 区分，不因更换 Bot 混用。
