# 影视刮削应用设计访谈

日期：2026-11-14。需求访谈的产品决策已确认；本文区分已确认设计、当前源码事实和验收结果，设计确认不代表代码实现或交付验收已经完成。

下文“已核对的项目现状”保留设计访谈时的源码事实；后续实现与本次实际验收另见[实现记录](media-scraper-implementation.md)。

## 2026-11-14 简化交互后的当前决策

用户在实际使用后明确要求：“简单选择目录，点开始刮削就能完成整个目录刮削”，并对补充问题回答：“q1，不确定的直接跳过，q2，不后台进行”。本轮决策覆盖下文旧版 Q9、Q16、Q20、Q27 中的人工选择和确认流程：

- 主流程为选择目录、点击开始、自动处理整个目录和全部子目录、显示结果；读取全部分页，不要求逐页选片、预览确认或候选选择。
- 按影片番号筛选精确匹配，同一番号的不同资料源按后端顺序自动尝试，采用首个可用详情；一个来源不可用时继续下一个，同批次同号分段复用已采用来源。无法识别影片番号、无同号匹配、文件冲突或配套资料归属不明确时跳过，不在中途等待输入。
- 由当前页面连续推进步骤；停止或关闭页面停止后续操作，重新打开及宿主重启不自动续跑。
- 先完整扫描目录，再逐个番号检查并立即执行；同号分段仍一起核对目标和配套文件，不让后续影片的联网查询阻塞前面已经匹配的影片。来源或已确认的单项执行失败记录原因后继续其他影片；提交结果不明、目录授权改变或任务记录无法确认时停止。这一项覆盖旧 Q38 对所有连接故障统一暂停整目录的处理。
- 散放视频按番号整理、保留视频原名、默认补齐缺失资料的既有规则继续适用。后端及覆盖选项移入设置，主流程不展开。
- 文件身份、位置、内容和提交回执仍由宿主核验；这些校验自动执行。结果中提供未完成项的手动重试，重试前自动核实普通中断；恢复记录仍只供查看。

`media-scraper 0.1.1` 将“不确定”错误地扩大为“多个资料源”，导致标准路径 `/视频/AV/SONE-614/SONE-614.mp4` 被跳过。用户反馈后实际核对，公共后端的 FANZA 与 JAV321 两条结果均为 `SONE-614`。`0.1.2` 按上述规则纠正为同号来源自动尝试；来源全部不可用时显示来源失败，不把它解释为影片无法识别。

后续实际页面中，`0.1.2` 仍有大量已匹配视频停在等待、整批尚未写入的情况；页面关闭后来源错误又只剩“未取得匹配的资料”。`0.1.3` 改为逐番号完成检查、执行和保存结果；每次目录任务统一保存清单、来源错误及已提交步骤，重试前根据宿主记录核实，缺失清单或无法核实的记录只供查看。暂时的搜索和详情故障最多自动重试一次，停止会取消重试；已写入部分分段后固定同号来源。

插件继续兼容宿主 0.3.10 起的既有接口。下文各轮确认保留为历史设计，涉及交互冲突时以本节为准。目录简化的历史验证记录位于插件仓库 `docs/media-scraper-simple-validation.md`，来源修复及实例验证位于 `docs/media-scraper-0.1.2-validation.md`，逐部执行和错误记录验证位于 `docs/media-scraper-0.1.3-validation.md`。

## 已提出的需求

- 新增一个应用 app，为指定文件夹提供影视刮削服务。
- 首期使用 MetaTube 后端，结果写回网盘，适配 TGDrive 影视应用 Cinema 和飞牛影视客户端。
- 首期只能由用户手动进行刮削，不设计后台自动执行。
- 使用 grill-with-docs 流程逐轮澄清，并在概念和决策确认后更新术语与必要的 ADR。

| Q41：同番号多视频播放 | Cinema 保留各视频的独立播放入口；同番号的不同版本默认不自动连续播放，首期分段视频也由用户手动切换，不仅凭同目录位置建立自动连播关系。 |

## 公共验收后端调查与指定服务核验

用户在第七轮明确指定 `https://metatube-server.hf.space/`。2026-11-14 01:58:43–02:00:56（北京时间）已完成本次匿名资料源、搜索、详情、主图链路核验，请求未携带 Token、账号或 Cookie。结果如下：

| 核验项 | 请求 | 实际结果 |
|---|---|---|
| 资料源 | `GET /v1/providers` | HTTP 200；`{data:{actor_providers, movie_providers}}`，两个字段均为资料源名称到网址的映射。 |
| 默认搜索 | `GET /v1/movies/search?q=IPX-001` | HTTP 200；`{data:[…]}`，唯一候选为 `provider=JAV321`、`id=ipx00001`、`number=IPX-001`。 |
| 候选详情 | `GET /v1/movies/JAV321/ipx00001` | HTTP 200；`{data:{…}}`，身份字段与搜索结果一致。 |
| 主图 | `GET /v1/images/primary/JAV321/ipx00001` | HTTP 200、`image/jpeg`，实收 64,696 字节；JPEG 标记与完整解码通过，358×538 像素。 |

样本海报仅接近 2:3，不能证明后端保证精确比例或所有图片都不超过 2 MiB，宿主仍需按 Q24 验证与处理。详情中的上游图片地址使用 HTTP，本次核验使用指定后端的 HTTPS primary 接口；应用也沿用候选返回的 provider 和 ID 获取图片。

固定单来源时，JavBus 的所测编号返回 404，FANZA 返回 500，MGS 返回 403；默认搜索通过 JAV321 成功，不能将单来源失败直接归因为整个后端需要 Token。评分样本没有满分或量表字段，继续遵守 Q32。

## 已核对的项目现状

- [领域术语](../GLOSSARY.md)中的“网盘目录”指 TGDrive 网盘目录树中的目录，区别于服务器本机目录；“页面应用”和“服务插件”也有不同含义。
- 普通应用包是沙箱内运行的静态资源，不能直接连接任意外部服务。宿主能力通过方法白名单和权限检查开放，见 [应用开发说明](apps.md)、`src/apps/runtime.rs` 与 `frontend/src/apps/bridge.ts`。
- 当前清单允许 `files.read`、`media.read`、`favorites.write` 和固定应用使用的 `fntv.service`，没有通用网盘文件写入权限，见 `src/apps/package.rs`。
- 飞牛影视兼容服务可读取同目录 NFO 和海报；现有索引不执行联网刮削，见 [飞牛影视兼容设计](fntv-compatibility.md)与 `src/apps/fntv/index.rs`。
- 当前 Cinema 根据文件名得到标题和集数，不读取 NFO；FNTV 读取 NFO 的标题、简介和年份，电视剧另读取季、集与剧名，但尚不完整消费演员、评分、类型等描述信息。写入 NFO 不能直接视为两端都能完整展示，见插件仓 `cinema/model.ts` 与宿主 `src/apps/fntv/index.rs`、`src/apps/fntv/protocol.rs`。
- 同视频基本名的 JPEG 海报是当前 Cinema 与 FNTV 都能读取的文件形式。FNTV 当前同目录海报限制为 2 MiB、NFO 限制为 64 KiB；Q24 已确认新海报不超过 2 MiB，Q40 已确认同步将两端 NFO 读取上限适配到 1 MiB 并移除当前单字段 4 KiB 限制。
- `ui.task` 只展示当前应用页面的任务状态，关闭页面会清理；它不是持久后台调度器。应用封面库属于可淘汰缓存，也不是网盘海报产物，见 `frontend/src/apps/views/AppHost.vue` 与 `src/apps/covers_db.rs`。
- 当前 `Db::move_node` 只更新单个节点，保持节点 ID 与文件内容版本；单独移动视频不会连带移动字幕、NFO 或海报。创建目录与移动节点也不是一项组合事务，整理任务需要新增相应编排与恢复能力，见 `src/db/tree.rs` 与 `src/vfs.rs`。
- 普通 VFS 上传完成时可能原子替换同名 ready 文件；“默认补缺”必须使用不可覆盖的提交策略并在提交时检查冲突，不能仅在上传前检查文件是否存在，见 `src/db/upload.rs`。
- 当前可恢复上传有不可覆盖提交、完成／取消幂等回执和结果查询，可以用于手动核实文件写入，无须新建自动刮削调度器。浏览器取消请求并不确认服务器已经停止写入，新入口需提供相应的结果与中断契约，见 `src/db/resumable.rs`、`src/api/uploads.rs` 与 `frontend/src/apps/bridge.ts`。
- 普通 `app_settings` 和 `app_data` 没有专用秘密字段，回读会返回原值，且会进入数据库及应用更新恢复快照；Token 保存方式需要专门落实，见 `src/apps/package.rs`、`src/apps/db.rs`、`src/apps/lifecycle_db.rs` 与 `src/backup.rs`。
- Cinema 海报框为 2:3；原图不超过 8 MiB 和 1600 万像素。FNTV 同目录海报限制为 2 MiB。公共 `movie.nfo`／`poster.jpg` 可以供同目录多视频使用，但同视频基本名的专属资料优先；仅写“番号.nfo／番号.jpg”不能保证原名不同的视频命中资料。
- FNTV 现有协议含 `original_title`、`release_date`、`vote_average`、`genres` 字段，部分仍为占位值；官方客户端对演员、导演、厂商和电影系列的对应字段尚无已核对证据。资料写入 NFO 与官方客户端展示能力需要区分。
- 两端都按去掉最后一个扩展名后的基本名关联配套文件；同基本名的 MP4、MKV 会共用 NFO、海报和字幕，单独移动其中一个视频及这些文件会影响留在原处的另一个视频，见 `cinema/model.ts` 与 `src/apps/fntv/index.rs`。
- FNTV 的专属 JPEG 顺序为 `基本名-poster.jpg`、`基本名.jpg`，然后目录共用海报；Cinema 当前不识别 `基本名-poster.jpg`，且共用海报候选集合也不完全相同。两端消费同一资料仍需统一已有文件识别与优先级，见 `src/apps/fntv/index.rs:335` 与 `cinema/model.ts:46`。
- FNTV 的 NFO 除整份 64 KiB 上限外，单个原始 XML 标签内容超过 4096 字节也返回空值，长简介可能完全不显示，见 `src/apps/fntv/index.rs:135`。
- Cinema 当前把同目录视频列成独立按钮，默认开启自动连播，尚不区别分段和不同版本，见 `cinema/main.ts:308`、`cinema/main.ts:520` 与 `cinema/model.ts:32`。
- FNTV 当前有媒体库合计 3000 条视频的首期索引上限；新刮削应用的目录扫描能力不会自动提高消费侧索引容量，见 `src/apps/fntv/index.rs`。
- 当前 `Db::move_node` 的源、目标检查与更新未组成事务，也不接受预览中所见的原父目录、名称和内容版本；可恢复上传虽有覆盖开关，但没有“仅覆盖预览中那个文件及其内容版本”的提交条件。新的整理及覆盖接口需要补齐提交时条件核对，见 `src/db/tree.rs` 与 `src/db/resumable.rs`。
- `app.lifecycle` 的持久租约用于应用数据结构迁移，不是通用的手动刮削批次租约；首期单个执行批次和关页中断规则不能仅复用该名称来保证，见 `src/apps/lifecycle_db.rs`。
- 文件内容版本不包含名称、父目录和修改时间，目录内容版本也不代表子树变化；预览核实必须分别检查文件身份及内容、当前位置、目标位置和配套资料集合，见 `src/db.rs:70`。
- 上传完成／取消回执只保留 7 天，且备份会清除回执；30 天刮削历史需要独立操作记录。应用更新恢复也会还原旧配置及私有数据，但不回退真实网盘位置和资料文件，见 `src/db/upload.rs:258`、`src/backup.rs:526` 与 `src/apps/lifecycle_db.rs:145`。
- 当前任务条取消只发送 `task.cancel` 事件，关页握手及浏览器请求中断不构成宿主操作停止确认；对已完成上传调用取消也可能返回成功，需要核对提交结果后才显示已停止，见 `frontend/src/apps/views/AppHost.vue:88`、`frontend/src/apps/bridge.ts:76` 与 `src/db/resumable.rs:386`。
- FNTV 当前按视频节点保持独立影片 GUID 和单文件播放入口；没有已核对的宿主开关能控制官方客户端跨影片自动连播偏好，Q41 的默认行为调整针对 Cinema，见 `src/apps/fntv/index.rs:408` 与 `src/apps/fntv/protocol.rs:573`。

## 已核对的 MetaTube 边界

- 已核对的 MetaTube 默认资料源与官方命名说明主要面向番号成人影片及演员。不能因为接口命名为 `/movies`，就认为已有普通电影或电视剧季集适配。
- 官方命名说明包含有码、素人、无码及 FC2 等类别；默认资料源包括 FANZA、MGS、JavBus、FC2、HEYZO、Caribbeancom 等。
- `MovieInfo` 的 `series` 是资料字段，当前模型没有电视剧的季、集层次。
- 后端提供元数据 JSON 和图片，不负责生成 NFO、列出 TGDrive 网盘内容、移动视频或播放正片；这些能力需由新应用与宿主实现。
- 搜索候选的 `number` 是作品番号，详情查询使用候选返回的 `provider + id`。候选中的 `score` 是来源影片评分，不是文件识别置信度，不能用它判断是否匹配了正确文件。
- `MovieInfo` 没有独立原名或翻译标题字段；上游插件在翻译前保存收到的 `title` 作为 OriginalTitle。`label` 是单个发行品牌，`series` 是系列，`genres` 是分类，不能混作同一字段。
- `score` 缺少统一满分与量表信息；上游插件乘二并不能证明所有资料源均采用五分制。Q32 已确认保留来源原值，仅在量表明确时写入通用评分及满分。
- primary 图片默认按 2:3 裁剪并输出 JPEG，但没有 2 MiB 大小保证；需由宿主验证并在必要时缩放、重编码，才符合 Q24。

此次核对的 HTTP 契约：

| 接口 | 已核对的行为 |
|---|---|
| `GET /v1/providers` | 返回当前后端启用的资料源；无需 Token，不能只根据源码默认注册假定用户后端可用。 |
| `GET /v1/movies/search` | `q` 必填，`provider` 可选，`fallback` 默认开启；无结果返回 HTTP 404。 |
| `GET /v1/movies/:provider/:id` | 查询候选详情；`lazy` 默认为 true，优先使用后端缓存。 |
| `GET /v1/images/primary/:provider/:id` | 返回主图 JPEG，可使用后端裁剪参数；与 thumb、backdrop 一样不经过 Token 中间件。 |
| 搜索与详情鉴权 | 后端配置 Token 后使用静态 `Authorization: Bearer`；不是独立用户登录或刷新令牌流程。 |
