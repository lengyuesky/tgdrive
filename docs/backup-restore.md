# 备份与恢复

自动备份为主库与各应用 SQLite 分别生成一致性快照，再将同一归档投递到全部已启用渠道（Telegram、WebDAV、S3）。各渠道独立保留最近 7 份、独立重试；可设置备份密码，归档先用 age 加密再离开本机。

- **新备份**为 `.tar` 或 `.tar.age`。主库包含网盘索引、设置、安装/授权记录和应用 KV；每个应用的固定业务库单独归档。
- **WebDAV 与 S3**保存完整归档。**Telegram**使用独立的备份分块设置，默认每块 18MB，按整组保留和清理，不留下半组。
- **下载数据库备份**得到明文 `.tar`，不受远端备份加密开关影响；包含应用主动保存在 SQLite 中的秘密，应与主库同等保护。
- **旧 `.db` / `.db.age` 单文件备份仍可恢复**，不要求先转成归档。旧备份没有应用库时，不将当前旁路应用库混进恢复结果。

归档只接受以下固定普通文件，并核对格式、路径、重复项、长度、SHA256 和 SQLite 完整性；拒绝链接、设备文件和任意解包路径。

```text
manifest.json
host.sqlite3
apps/<应用 ID>/app.sqlite3
```

归档不包含应用包、可再生缓存、私有临时目录、运行套接字或 `-wal` / `-shm` 文件。应用包仍按已记录摘要重新物化；缓存由应用重建。

## 在线应用库快照

应用持久业务状态只放 `state/app.sqlite3`。宿主派生一个以该应用独立 UID/GID 运行的备份辅助进程，清空宿主环境，只提供固定 PATH、语言、HOME 与 TMPDIR。辅助进程用 SQLite Online Backup API 读取包含已提交 WAL 的一致快照，通过有界管道流回宿主；应用后端继续运行。

root 不按应用可控路径打开原始业务库。类型、所有者、单一链接与固定库路径都要核对；辅助进程仍受该应用的文件权限边界约束。快照失败、超时、库被替换为链接，或主库快照之后安装 generation 改变，均放弃本轮，不投递半份备份、不删除上次成功备份。取消辅助进程只回收它自己的进程组，不误杀继续服务的后端。

**不同数据库分别一致，不承诺共同事务时点。** 恢复后应用应依据最新文件内容版本和变更游标核对派生索引，不自动继续未知写入。

## 无变化时跳过

「每日自动备份」可开启**无变化时跳过**。主库修订号由写入触发器随事务维护，各渠道独立保存成功基准；某渠道失败不影响其他渠道。从未成功备份的渠道总会先得到完整备份，手动立即备份不跳过。

文件与目录、分享、存储配置、后台设置、应用 KV 等实质数据算变化；备份状态、维护日志等运行状态不算。**存在应用 SQLite 时，不能只用主库修订号证明业务库未变化，所以当前仍按日取整份归档并投递。** 应用自行管理 schema，宿主不注入业务触发器或伪造统一修订。

修改 WebDAV URL，或 S3 端点、桶、前缀、Access Key 后，程序不会跨目标删除旧备份；旧位置由主人自行清理。

## 从 Telegram 频道恢复

在「系统设置 → 备份」选择「从 Telegram 恢复」，可探测频道、选择已记录备份，或输入备份消息链接/ID。全新部署先配置存储 Bot、频道、MTProto API ID/Hash 和网页登录账号密码。后台配置优先于环境变量。

探测按每批 100 个消息位置读取，找到最近 5 份完整备份即停止；按文件名组合非连续分块，缺块、重复和不一致的分块不能恢复。探测只读消息，不发消息、转发或删除，也不把探测结果加入自动清理队列。没有 MTProto API ID/Hash 时仍可手动提供全部分块消息链接。

开始下载预检需要主人明确同意：指定消息会**临时转发回同一频道**，完成后只清理本次临时消息，不删除来源备份。Bot 必须可访问和发消息，禁止转发的频道不支持；缺少删除权限时残留临时消息需手动清理。

向导下载、按编号合并、解密（如有）、校验主库与各应用库，再试迁移。加密密码与登录密码用途不同；密码错误、文件损坏、应用库摘要不符或备份版本比宿主新，都不能确认恢复。归档摘要证明完整性，不证明来源可信，只恢复自己的可信备份。

单次最多 128 块，密文、明文和归档内容分别不超过 8 GiB；准备任务与就绪候选各有 30 分钟时限。暂存、试迁移与回滚需要额外空间。age 工作因子最高 20，密钥派生峰值内存约 1 GiB；超限旧备份应在受控环境离线解密。

**确认恢复会覆盖当前网盘索引、后台配置与对应应用库。** 查看摘要后输入「恢复」、当前登录密码和已启用的两步验证码。恢复只接受主人的强认证会话，WebDAV 应用密码不能授权；保留当前实例的登录安全设置和网络代理，不恢复旧登录会话。

恢复不是在线替换：先阻止新写入，停止并等待全部应用进程组及子进程回收，服务退出。下一进程在开连接池前生成包含 WAL 的本机回滚快照（主库及应用库），再切换并验证。中断或验证失败回滚整组数据库。Compose 会自动重启；直接运行需由进程管理器拉起，或再次执行 `tgdrive serve`。

恢复后重新分配应用 generation/run_id，清缓存、临时目录、运行目录、旧票据及游标 epoch，只恢复已验证记录和固定业务库。不自动重新上传 Telegram 文件。回滚副本同样包含秘密，不能公开上传。

默认进入**安全模式**，暂停旧上传清理、消息删除、迁移、自动备份和 Bot 收件；检查结果后，在备份页再次认证并明确解除安全模式。**未完成收件不随备份恢复继续执行**：导出只将快照中的旧待办失效，不改在线待办；恢复也结束旧未完成收件，已完成记录与网盘文件保留。正常服务重启的待办续跑规则不变。

## 下载归档后的离线恢复

Telegram 多块备份先按编号合并；WebDAV/S3 完整文件不需要合并。把下载内容放进独立目录，不从其中执行脚本。

```bash
cat tgdrive-backup-YYYYMMDD-HHMMSS.tar.part*-of-* > backup.tar
# 加密分块先合并为 backup.tar.age，再解密；单块直接使用原文件。
age -d -o backup.tar backup.tar.age
# 或使用宿主自带的 decrypt-backup 子命令。
```

停止服务后使用 `restore-backup`，它与向导共用路径/数据库校验、当前安全设置保留、主库加应用库回滚及安全模式，不要直接用 tar 向数据目录解包。

```bash
docker compose stop tgdrive
# 将下载文件放到 ./backup/backup.tar；本次只读挂载，不把下载目录当作工作目录。
docker compose run --rm -v "$PWD/backup:/restore:ro" tgdrive restore-backup /restore/backup.tar
# 按提示输入“恢复”，成功后再启动。
docker compose up -d tgdrive
```

`restore-backup` 也接受解密后的旧 `.db`，与运行服务共用实例锁；服务未停止时拒绝恢复。新归档不能只取出 `host.sqlite3` 替换主库，否则会丢失对应应用业务库。备份密码丢失后，加密备份无法解密。

## 账号安全

- 登录密码使用 argon2id 哈希；「导出 .env」也是哈希，不是原密码。
- 两步验证支持 TOTP 与一次性恢复码。网页登录密码不能绕过已启用的两步验证；WebDAV/Basic 使用单独应用密码。
- 验证器和恢复码都丢失时，停止服务后运行 `docker compose run --rm tgdrive reset-2fa`，再启动；写库子命令与服务共用实例锁。
- 远端快照剔除宿主登录、设备和 MTProto 会话凭据；应用自己保存的秘密不由宿主解释或删改，务必启用远端备份加密并保护明文下载及本机回滚副本。
